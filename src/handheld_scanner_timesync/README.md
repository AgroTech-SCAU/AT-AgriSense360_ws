# handheld_scanner_timesync

Read-only ROS 2 adapter for the **TimeSyncV2** mainboard
(STMicroelectronics USB CDC, `0483:5740`).

The node polls the board's documented query commands and publishes
`handheld_scanner_interfaces/msg/TimeSyncStatus` on `/system/time_sync/status`.
It never sends configuration commands (`CAMCFG`, `CAMENABLE`, `RADARARM`,
`TIMEMODE`, `SAVE`, ...).  Changing hardware behaviour remains an explicit
operator action through the vendor web console or a future dedicated service.

## Why this node exists

The board's hardware outputs (camera trigger, LiDAR PPS/RMC) are generated by
the STM32 and do **not** depend on the host.  The USB CDC link exists to:

- observe the time source and PPS/RMC/GNSS validity;
- read the cumulative trigger pulse counters for end-to-end pairing;
- record `LOCAL` versus `GNSS` state in the bag metadata.

Closing this node does not stop scanning.

## Protocol

- `115200 8N1`, ASCII, CRLF, one command at a time.
- Replies are `COMMAND key=value ...`.
- Polled commands: `TIME`, `IO`, `CAMERA`, `RADAR`, `LINK`.
- `CAMERA ... pulses=...` is a cumulative counter since power-on.  `pulses[0]`
  is CAM1, the only channel wired to the MF287 four-camera module.

## Field mapping

| Board reply | TimeSyncStatus field |
|---|---|
| `TIME mode/state` | `time_source`, `utc_status`, `pps_locked` |
| `TIME rmc_valid` | `gnss_rmc_valid` |
| `TIME pps64` | `pps_count` (GNSS input PPS count) |
| `TIME freq_ppb / 1000` | `frequency_correction_ppm` |
| `CAMERA pulses[0]` | `trigger_count` (CAM1, cumulative) |
| `RADAR active=1` | `lidar_sync_reported` |
| raw snapshot | `detail` |

`holdover_seconds` and `estimated_clock_error_ns` stay zero because the board
reports a holdover flag and a residual without a documented unit.  The raw
values are kept in `detail`.

`camera_clock_mapping_valid` is false: the camera clock mapping requires a
calibrated Camera-IMU/LiDAR setup and is not provided by this board.

## Run

```bash
colcon build --symlink-install --packages-select handheld_scanner_timesync
source install/setup.bash
ros2 launch handheld_scanner_timesync handheld_scanner_timesync.launch.py
```

The whole device is started through the single bringup entry:

```bash
ros2 launch handheld_scanner_bringup handheld_scanner.launch.py enable_control:=true
```

`enable_control` defaults to `false`, so existing v0.2 launches are unchanged.

## Port ownership and stable aliases

The vendor web console and this node cannot open the device at the same time.
The node requests an **exclusive** lock; if the console or a second node
already holds the port, the node logs the open error and retries instead of
silently competing for reply bytes.  Close the console before starting it.

Never address the board as `/dev/ttyACM0`.  USB enumeration order changes when
the GNSS receiver is plugged in first.  Install the provided rule and use the
stable aliases:

| Alias | Device |
|---|---|
| `/dev/handheld-scanner-timesync` | TimeSyncV2 mainboard (`0483:5740`) |
| `/dev/handheld-scanner-gnss` | Septentrio mosaic-G5 USB1, NMEA/command (`152a:8231`, interface 00) |
| `/dev/handheld-scanner-gnss-aux` | Septentrio mosaic-G5 USB2, SBF/debug (interface 02) |

```bash
sudo cp config/70-handheld-scanner-serial.rules /etc/udev/rules.d/
sudo udevadm control --reload-rules
sudo udevadm trigger --action=change --subsystem-match=tty
```

The rule is numbered `70-` deliberately: it must run before systemd's
`73-seat-late.rules` so the `uaccess` tag generates an ACL.  It also sets
`GROUP="plugdev"` as a fallback for non-seat sessions and adds
`ID_MM_DEVICE_IGNORE` so ModemManager does not probe the ports.

`TimeSyncStatus.header.stamp` is the host time at which the poll cycle was
published.  It is not the board's device time; `detail` carries `mode`,
`state`, `utc_now`, `time_now` and the firmware identifier for that.

```bash
colcon test --packages-select handheld_scanner_timesync
colcon test-result --verbose
```

The protocol tests use recorded reply lines and do not need the board.
